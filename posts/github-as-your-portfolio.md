# GitHub as Your Portfolio: Why I Archived a Full Portfolio Site for a README

*2026-04-08 · github, portfolio · GitHub is Your Portfolio*

I had a portfolio site that was 85 percent complete — real interactive tools, real product decisions, real work in it. I had a GitHub profile that read like a resume. I was spending attention on both and neither was getting what it deserved. The uncomfortable realisation was that the site, polished as it was, signalled the wrong thing: "I designed something to look impressive." The GitHub profile, rough as it was, was where the actual credibility would need to live. I had to pick one and commit.

## Context

By April 2026 I had two portfolio presences:

A GitHub profile with sections covering what I work on, my current builds, and the tools I use. The tone was right. But it read like a resume, not a case study.

A React portfolio site built in Lovable, deployed on Vercel, with two real interactive tools:

- A Decision Log where visitors could see 8 real product decisions, pick what they would have done, and then see what actually happened
- A Tech Fluency Companion where you could type a technical term and get three levels of explanation written for product managers

The site was roughly 85 percent complete. I had real work in it. Real decisions. Real tools.

I archived it.

## The Reasoning

The decision came from a single observation: product managers are shifting toward building and creation, and GitHub is increasingly where that credibility lives.

A portfolio site signals "I designed something to look impressive." A well-crafted GitHub profile signals "I actually ship things."

The world is changing fast here. Non-technical PMs are now expected to understand engineering constraints more deeply. Companies want PMs who can evaluate technical tradeoffs, not just translate requirements. A GitHub presence that shows you genuinely build things is a stronger signal than a polished marketing site that describes it.

Maintaining both was also a focus problem. Every hour spent on the portfolio site was an hour not spent building real projects. Two presences meant neither got the attention it deserved.

The tradeoff accepted by this decision: the portfolio site had interactive tools that GitHub cannot replicate — a Decision Log where visitors could see real product decisions and compare their choices, a Tech Fluency Companion that explained technical terms at three levels for PMs. Those tools are gone from public view. The cost was real. The reasoning was that a strong GitHub presence with three great project READMEs would compound over time in a way the portfolio site would not, because GitHub is where work actually lives.

## What a GitHub Portfolio Actually Requires

The standard GitHub profile is a wall of green squares and a list of repositories. That is not a portfolio. That is an activity log.

A real GitHub portfolio requires deliberate design decisions:

**The profile README is the homepage.** It needs to do what a portfolio site homepage does: communicate who you are, what you build, and why someone should care. Not in a corporate bio format. In a narrative format.

**Each repository README is a case study.** The technical documentation is there already. What is missing is the product narrative: what problem this solved, who it was for, what you discovered, and what the results were. Engineers write READMEs for other engineers. A PM writing a README for a mixed audience needs to add the layer that explains why the thing exists.

**The stack signals your perspective.** My original profile had generic developer tools listed (TypeScript, React, Tailwind). I replaced them with the AI toolchain I actually use: Claude Code, Lovable, Supabase, Vercel, NotebookLM, Mixpanel. The list tells a story before anyone reads a word.

## What I Changed in This Session

This session started as a quick edit: rename the "Tech stack" section to "Stack I Reach For" and update the tools listed. It turned into a full strategic decision.

The tags I removed: Claude Code, Notion, NotebookLM, React, Vite, Tailwind, GitHub, Vercel, SQL, Mixpanel, GA, Tableau, Figma.

The tags I replaced them with: Supabase, Vercel, Claude Code, Cursor and Cowork, ChatGPT, Lovable, NotebookLM, Figma, Mixpanel, SQL.

The difference is not just the specific tools. The original list looked like a developer who also uses some AI tools. The new list looks like a product manager who builds with an AI-native stack. That is a more honest representation and a more differentiated one.

## What Comes Next

The strategic decision is made. The remaining work is execution:

Rebuild the profile README as a narrative homepage, not a formatted resume. Add case study READMEs to the main projects. Curate the six pinned repositories to tell a coherent story about what I build and how I build it.

The portfolio site repository will stay public with an archived notice. The code is real. The tools inside it were real. But active investment goes to GitHub from now on.

## What I Learned

**Two presences mean neither gets full attention.** Pick one and invest in it properly.

**GitHub credibility comes from narrative, not activity.** The green squares do not tell anyone what you built or why. The README does.

**Your tool list is a positioning statement.** It communicates your perspective before anyone reads a word. Choose it deliberately.

**An incomplete but focused presence beats a complete but scattered one.** A well-crafted GitHub profile with three great project READMEs is more credible than a polished portfolio site and a mediocre GitHub profile.

**The decision lesson: archiving something real costs something real.** This was not a clean choice between a bad option and a good one. The portfolio site had genuine value that no longer exists publicly. The decision was correct, but "correct" did not mean "free." Any PM who has had to sunset a feature their users liked knows this feeling. The right call is still a loss. Acknowledging that is part of making the next right call with clear eyes.
