# A knowledge base an LLM can query, with no vector database

*2026-07-28 · ai, knowledge-management, engineering, cost-thinking*

Every "let an LLM query our internal docs" project reaches the same fork almost immediately: stand up a vector database and embed everything, or don't. It looks like an engineering choice, but underneath it is a resourcing decision, whether the document count and query volume actually justify paying for and maintaining infrastructure before you have any proof you need it. For a shared knowledge base I was building for an internal documentation repository, that call had already been made in an earlier planning spec, before any code existed: below a certain document count, a well-maintained index costs less, in money and in complexity, than a vector store, and this repository was nowhere near the count where that trade flips. The interesting part was not making that call. It was what it took to trust it enough to ship it, and the one test that proved it was a decision, not just an assumption sitting in a spec.

The plan was simple to state and easy to get wrong in practice: instead of embeddings, generate a single index file where every document in the repository contributes exactly one summary line. An agent that wants to answer a question reads the index first, a small file that is cheap to read even as the repository grows, matches the question against those one-line summaries, and opens only the specific documents that look relevant. Only if nothing in the index matches does it fall back to a full-repository grep. No similarity scores, no embedding model, no vector store to stand up, license, or maintain. Just a list of summaries and a human deciding, document by document, what one line should say about it.

The part I had to get right was making that one line non-negotiable. Every document in the repository carries frontmatter, and one field in that frontmatter, `summary`, is the entire retrieval unit. It is not a description for someone who already has the file open. It is the only thing an agent sees before deciding whether to open the file at all. A missing or vague summary does not just weaken retrieval, it makes the document invisible to both query paths I designed: the direct agent-reads-the-repo path, and a future two-call Q&A path where a model first picks a handful of file paths from the index and then reads only those. So the indexing script does not silently skip a document with no summary. It flags it visibly in the generated index as missing, because a silent gap is a worse failure mode than an ugly one you can see and fix. A resourcing decision to skip a vector database only holds up if the cheaper alternative fails loudly when someone cuts a corner, not quietly.

That script, a small zero-dependency Node program, walks every markdown file, reads its frontmatter, and regenerates the index as a flat list, one line per document. Writing it was the easy part. The part that actually tested the decision was whether the automation around it would hold up when I was not the one keeping it in sync, because a cost-saving architecture that only works if a human remembers an extra step every time is not actually cheaper, it just moves the cost onto someone's memory.

So I did the thing that turns a decision into a verified mechanism instead of a diagram: I pushed a real new document into the repository without pre-generating the index locally first. That is the failure mode the whole system exists to prevent, a document landing in the repo with no matching line in the index, silently unreachable to any agent that trusts the index instead of grepping everything. If the automation did not catch that, the entire "structure beats a vector database, at this scale" argument was just an assertion I had not actually paid for testing.

It caught it. A workflow configured to run on every push to the main branch detected the diff, ran the indexing script, and committed the regenerated index file directly back to the repository on its own, no pull request, no human step in between. That direct-commit behavior is a deliberate, narrow exception to an otherwise strict rule that everything else in the repository goes through review. It is allowed here specifically because the script is fully deterministic, same documents in, same index out, and it touches nothing except that one generated file. The commit that resulted, `13c980b`, is the proof that this was not a resourcing bet I was hoping would pay off. It is a bet I watched pay off, end to end, without touching it myself in the moment it mattered.

What this replaced was the default a team defaults to without sizing the problem first: embed everything, trust the similarity search, add infrastructure to solve a problem that structure could solve for free at this scale. The corrected mental model is that a vector database earns its cost at a document count where a human curating one summary line per document stops being feasible. Below that threshold, the honest constraint is not retrieval quality, it is discipline about writing a good one-line summary for every document that goes in, and that discipline is now enforced by automation instead of relying on someone remembering to run a script before they push.

The lesson generalizes past this one repository: do not fund the infrastructure-heavy solution to a problem you have not yet sized. Vector search solves a real problem, the problem of scale, but paying for it before you have the scale that justifies it just hides a simpler mechanism, a human-written summary line, a deterministic index, an agent that reads before it greps, behind a system that costs more to run and is harder to reason about when it is wrong. The way to know which regime you are actually in is not to guess from a spec. It is to push a real change without the safety net and watch whether the cheaper thing you built catches it on its own.
